## Batch Scope

This batch makes the server discoverable to a human opening the repository: a short README section, a
tracked `.mcp.json` declaring the one server, and the `.gitignore` entry for the built binary. It is
one batch because the three files are one decision — the repository ships a working config, the
README points at it, and the faster pre-built alternative the README documents needs the ignore
entry. It depends on batch 2 only, not batch 3: nothing here reads a test.

No new documentation file is created. Plan §2 deleted V1's MCP setup document along with the rest of
the V1 surface and kept the README as a stub; a one-tool server needs a section, not a document.

## Batch Tests

`verify: go build ./cmd/quarry-mcp` is the right check for this batch, and the only meaningful one:
the batch adds no code and no test, but the shipped configuration's whole contract is that
`go run` against that package path works, so building that exact package is what proves the
configuration is not pointing at nothing. A test-suite invocation here would run tests unrelated to
anything this batch touches.

The README's claims and the configuration's behaviour against a real client are verified by the live
