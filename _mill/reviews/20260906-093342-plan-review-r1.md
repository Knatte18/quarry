## Findings

### [BLOCKING:design] LADDER_EXIT=1 triage rests on a false premise
**Location:** batch 1 / card 30, "Completion predicate" + "Aborted invocation"
**Issue:** Verified in `run.go`: `runCellRepetition` returns `repOutcome{incomplete: true}` on MaxAttempts exhaustion (no `abortRun`), and the post-run `CheckBlinding` fatal path returns `repOutcome{blindingFailed: true}` (no `abortRun`) — both apply here because all three kickstart cells are tool-less; `Run` folds either into `exitNonZero`, and `main.go`'s `summarizeAndReport` additionally exits non-zero whenever `summary.Incomplete`/`Invalid` is non-empty. A fully completed matrix therefore exits 1, and `blinding_failed_count > 0` does not imply a memory-path taint.
**Fix:** Split the `LADDER_EXIT=1` branch: only a repetition whose own `run.json` carries the `memory_path_scan` fatal finding is the abort case; an attempt-exhausted or gate-2 blinding-failed repetition is a completed run whose short arm card 31 dispositions, with no resume and no deletion.

### [BLOCKING:design] "exactly one offending target" is not observable
**Location:** batch 1 / card 29, contingency branch
**Issue:** Verified in `pack.go`: `RenderKickstartPack` returns on the *first* result whose `Error` is non-empty, whose `Status != StatusFound`, or which carries other than one symbol, so its error names exactly one target no matter how many failed; and `Pack` returns before `os.WriteFile(resolvePath, ...)`, so no `pack-resolve.json` exists to enumerate the rest. The gate that separates "one failure → substitute" from "two or more → halt" therefore has no input, and the plan's cascade would substitute repeatedly instead of halting.
**Fix:** Have card 29 enumerate the full resolve set independently (e.g. one batched resolve over `pack_targets` read out before substituting) and state that the halt test is over that enumeration, not over the pack command's single-target error message.

### [NIT:consistency] Lock path asserted as `~/.cache/ladder-eval`
**Location:** batch 1 / card 29 preflight step 2; card 30 poll + resume precondition 2
**Issue:** `worktree.go`'s `resolveWorktreeRootBase` resolves `LADDER_WORKTREE_ROOT`, else `XDG_CACHE_HOME/ladder-eval`, else `~/.cache/ladder-eval`; `AcquireRunLock` writes `.ladder.lock` under that resolved root. The plan states the third alternative as fact and instructs deleting a file there.
**Fix:** Say "the resolved worktree root (`LADDER_WORKTREE_ROOT`, else `$XDG_CACHE_HOME/ladder-eval`, else `~/.cache/ladder-eval`)" once, and reference it in all three places.

### [NIT:consistency] Card 30 declares `Deletes: none` but authorises a deletion
**Location:** batch 1 / card 30
**Issue:** The card's inventory says `Deletes: none` while its Requirements permit deleting `raw/<cell>/<rep>/` under the memory-taint disposition; the two statements contradict each other even though the path is git-ignored.
**Fix:** Name the conditional deletion in `Deletes:` (or state in the card that the raw tree is outside the declared inventory because it is ignored).

### [NIT:scope] Cross-check command does not name its repository
**Location:** batch 1 / card 29, contingency step 6
**Issue:** `git show 72c23d9:<file>` is written without a repository; `72c23d9…` is the loomyard pin from `ladder-kickstart.yaml`'s `tasks.07-fabric-merge-state-tracing.pinned_sha` and does not exist in the quarry worktree the card otherwise runs every command from.
**Fix:** Spell it against the read-only loomyard checkout (`git -C <loomyard checkout> show 72c23d9:<file>`) or against the pinned task worktree.
