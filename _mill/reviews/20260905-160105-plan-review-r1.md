## Findings

### [BLOCKING:scope] DeltaGit has no seam to the repository root
**Location:** batch 6 / cards 32–33 (and card 35's edit of `quarry/repo.go`)
**Issue:** Card 33 requires "Open the git layer against the same root the facade was opened with", but `DeltaGit(from, to, target)` takes no root, `quarry.Repo` holds only the unexported field `engine *engine.Repo` (`quarry/repo.go`), and `engine.Repo`'s `root string` is unexported with no accessor anywhere in `internal/engine/repo.go` — so no card in the plan makes the root reachable from package `quarry`.
**Fix:** Name the seam explicitly in card 32 or 33 — either a `root` field on `quarry.Repo` captured in `Open` (adding `quarry/repo.go` to that card's `Edits:`) or an exported root accessor on `engine.Repo` — rather than leaving it to cold-start invention.

### [BLOCKING:design] Delta text losslessness contradicts the reused symbol-line writer
**Location:** batch 7 / cards 39 and 41
**Issue:** Card 39 mandates reusing `writeSymbolLine` for every symbol the delta emits, but that function in `quarry/text.go` writes only File, Start, End, SigEnd, ID, Signature and Doc — never `Symbol.Kind` — while `created`, `deleted` and a `RenamedPair`'s two symbols carry `kind` in the JSON view with no other carrier; card 41's structural test ("every value present in the JSON view … appears somewhere in the text view") therefore cannot pass as written. Card 18's own const-replaced-by-var case (identical `id`, differing `kind`) is exactly where the two lines become indistinguishable.
**Fix:** Decide in card 39 whether the delta text grammar spells each symbol's kind alongside the reused line, or bound card 41's losslessness assertion to the fields the shared writer emits.

### [BLOCKING:scope] Stale `internal/cli` doc comments left uncorrected
**Location:** batch 8 / cards 42 and 44
**Issue:** The plan hunts false doc claims in cards 35 and 45 but not here: `parseArgs`' doc in `internal/cli/flags.go` states "The verb gate accepts exactly \"toc\", \"resolve\" and \"expand\"" and "--text and --root are valid for all three verbs"; `Run`'s doc in `internal/cli/cli.go` states it "switches on req.verb and calls one of runTOC, runResolve, or runExpand" with a default case "unreachable for every word other than the three verbs"; the `exitUsage` constant's own comment scopes the separator rejection to "a toc target". Both files are already in those cards' `Edits:`.
**Fix:** Add the three comments to cards 42's and 44's `Requirements:` as edits in the same commits, as card 45 already does for `internal/cli/doc.go`.

### [NIT:consistency] Mapping-function count disagrees within batch 8
**Location:** batch 8 / card 44 vs `## Batch Tests`
**Issue:** Card 44 says "the three existing mapping functions in this file", while the batch's own Batch Tests section says "all four existing mapping-function tables"; `internal/cli/cli.go` declares four (`codeForTOCError`, `codeForResolveResult`, `codeForExpandAnswer`, `codeForExpandError`).
**Fix:** Say four in card 44.

### [NIT:consistency] Card 10's toc-suite check is not in batch 2's verify
**Location:** batch 2 / card 10 vs `## Batch Tests`
**Issue:** Card 10 requires running "the existing `internal/engine` walk and toc suites", but the batch's `-run 'TestPackageClause|TestUnitsForClauseMap|TestClauseMapForFiles|TestWalk'` selects no toc test (they are named `TestRepoTOC_*` in `internal/engine/toc_test.go`), yet Batch Tests claims card 10's pass "rests on that same selection".
**Fix:** Either drop the toc half of card 10's claim or state that it rests on the repository-wide done gate.
