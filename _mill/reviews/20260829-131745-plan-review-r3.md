## Findings

### [BLOCKING:design] Cold configs execute through the main-matrix driver
**Location:** batch 6, cards 20/21/22
**Issue:** `plan_runs` is specified as all 45 pairs including the cold config (card 22 asserts "45 pairs ... all three cold-cell pairs strictly last"), and `run_matrix` iterates `pending_runs` unfiltered — so the three `a5-bundle-cold` runs are executed by the main pipeline, with no fresh per-`{n}` worktree, no `gate_cold_before`/`gate_cold_after`, and possibly a warm daemon, before `run_cold_cell` ever sees them; it then finds them `is_complete` and skips.
**Fix:** state in card 20 that `run_matrix` consumes only the non-cold subset, and give `run_cold_cell` its own pending-run filter over the cold config.

### [BLOCKING:scope] `warm_daemon` is defined but never called
**Location:** batch 6, cards 17/19/20/22
**Issue:** card 17 ships `warm_daemon` and says only "never called for a config with `cold: true`", but neither `execute_run` (card 19), `run_matrix` (card 20), nor the CLI order of operations (card 22) invokes it — while card 23's README documents "the pre-warmed daemon for the main matrix" as a run-environment fact. The warm-up's `mcp_call` `arguments` payload for `workspace_symbol` is also unspecified, so a malformed call would start no daemon silently.
**Fix:** name the call site and the `targets` payload the warm-up passes, and state whether it runs once per task worktree or once per run.

### [BLOCKING:scope] Batch 5 consumes batch 2 and batch 4 contracts it does not depend on
**Location:** batch 5 header + card 13
**Issue:** `depends-on: [1, 3]`, but `METRICS` names `usage.json` fields defined only by card 7 (`duration_ms`, `bash_grep_count`, `grep_tool_count`, `grep_fallback_total`, `denied_tool_attempts`) and `score.json` fields defined only by card 12 (`recall`, `precision`); card 13's `Context:` lists neither `extract_usage.py` nor `score_run.py`. Card 7 also nests the four token classes under a `tokens` mapping while `METRICS` lists them flat, and card 13 says only "flattened" without naming the source shape.
**Fix:** add 2 and 4 to `depends-on`, add both modules to card 13's `Context:`, and state the `tokens.*` flattening explicitly.

### [BLOCKING:scope] `probe.json` key contract is undefined for its reader
**Location:** batch 5 card 15 vs batch 6 card 18
**Issue:** card 15 requires `_meta.denied_tool_attempts_reported` "read from the run directory's `probe.json`", but the probe record is written by card 18 in a *later* batch under the field name `denied_tools_advertised`, and batch 5 neither depends on batch 6 nor lists any probe-schema source in `Context:`. The implementer of card 15 has no way to know which key to read. (Card 15 also says "run directory"; `probe.json` lives at the results root.)
**Fix:** pin the probe record's key names in card 15's `Requirements:` and cite card 18's field name explicitly on both sides.

### [BLOCKING:design] Redaction of the bare tool name `impact` destroys Ladder-B answer prose
**Location:** batch 4, card 11
**Issue:** `redact_text` replaces "every bare canonical quarry tool name from `QUARRY_TOOLS`" case-insensitively, and `impact` is one of the seven — so every occurrence of the ordinary word "impact" in a Ladder-B answer's `callers_to_update[].evidence`, `excluded_lookalikes[].reason`, and `open_questions` becomes `<tool>`, on a task that is literally an impact analysis. Card 11 names no exception and its tests do not cover the collision.
**Fix:** decide and state whether the bare-name pass excludes `impact` (redacting only `mcp__quarry__impact` and CLI forms), and add a test asserting an evidence string using "impact" as a common noun survives.

### [BLOCKING:scope] Cold-cell retry semantics are unspecified and collide with `build_worktree`
**Location:** batch 6 card 21, batch 8 card 26
**Issue:** card 26 requires a native-fallback cold run to be "invalidated and retried" and a different gate failing "three times" to halt, and card 21's "not-run" disposition presupposes "every attempt having failed" — but card 21 declares no attempt loop, no cap, and no worktree teardown on a failed attempt. Card 16's `build_worktree` "raises `HarnessError` when a directory already exists at that path", so a retry at the same `cold_worktree_template` `{n}` path fails on rebuild rather than retrying.
**Fix:** state the cold cell's attempt cap, the per-attempt worktree removal, and whether `MAX_ATTEMPTS` is reused.

### [NIT:consistency] Card 19's task-04 section-order rationale is wrong
**Location:** batch 6, card 19
**Issue:** the requirement states "the very next section in task 04 is its scoring notes, which name the three real callers and the decoy outright"; in the source it is `## Output schema (impact-analysis tasks)`, with `## Notes for whoever scores this` two sections later. The stop-at-next-`## ` mechanic is still safe, but the stated premise is false and the same card elsewhere depends on that schema section existing.
**Fix:** correct the rationale to the actual section order.

### [NIT:consistency] README run-environment omits `QUARRY_BUILD_TAGS`
**Location:** batch 7, card 23
**Issue:** the "Run environment" section lists "`QUARRY_STATE_DIR` cleared, `--state-dir` never passed", but card 17's `run_env` also scrubs `QUARRY_BUILD_TAGS`, and card 9 makes it load-bearing (a non-empty tag set appends a `tags-<hex>` segment at every `ResolveStateDir` tier and would fake a native fallback).
**Fix:** add `QUARRY_BUILD_TAGS` cleared, and the `QUARRY_CONFIG` non-scrub, to that section's list.

### [NIT:consistency] Fasit `_meta` block has no stated disposition in the scorer prompt
**Location:** batch 4, card 12
**Issue:** `build_scorer_prompt` embeds "the fasit" as one of three inputs; the committed `c.json` files carry a `_meta` block with `arm: "C"`, `see_also: "scorecard.md ..."`, and a `role` string containing the word "quarry" — fed verbatim beside an answer card 11 scrubs of exactly that word. It is identical across all 45 runs so it cannot leak *which* config, but the asymmetry is undocumented.
**Fix:** state whether `_meta` is stripped before the fasit enters the prompt.

## Verdict

REQUEST_CHANGES
Two orchestration gaps, two cross-batch contract gaps, and a redaction collision on `impact`.
