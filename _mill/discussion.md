```yaml
parent: main
```

## Problem

quarry answers "where is this symbol referenced" by asking a language server, and for Go that server is `gopls`. Two precision defects were inherited from loomyard's `internal/scoutengine` when the engine was extracted into this repo, and both were filed as GitHub issues (#2, #1) so they would not be lost in the move. Both trace to the same root cause: gopls's *default* query scope is not the scope a precise safety-gate tool needs.

The first defect is a false-negative one. `lspclient.go`'s `initialize` request sends no `initializationOptions`, so gopls never receives `buildFlags` and only ever loads the default build-tag view of a project. Every reference inside a file behind a `//go:build <tag>` constraint is invisible to every verb. Measured on loomyard — which uses `//go:build integration` / `//go:build smoke` for its test-tier separation — a large fraction of the true call sites to the two most heavily-tested benchmark symbols live behind that tag boundary and are never reported: `hubgeometry.Resolve` has 42 tagged call sites out of 68 real ones, and `hubgeometry.Layout.WeftWorktree` has 17 out of 38 — **59 of 106 combined** (`docs/scout-multilang.md:115`). Note that both that document's own headline (`:17`) and issue #2 state this as "40%", which the per-symbol counts on `:115` do not support; the counted figures above are the ones to trust, and correcting that headline is in this task's scope (see Scope → Documentation). There is no `--build-tags` flag to thread a tag set through.

The second defect is a false-positive one. `assert-no-callers <interface-method>` with no scoping flag returns every method matching that name and signature across every structurally-compatible interface in the workspace. Measured on loomyard's `internal/builderengine/poll.go` local `clock` interface (`Now() time.Time; Sleep(d time.Duration)`): **31 reported callers, 2 real** — the other 29 belonged to two unrelated `clock` interfaces independently declared in different packages, plus their test files. This is documented gopls behaviour for `textDocument/references` on an interface method, and the wrapper passes the noise through as a genuine violation. A `--within <dir>` flag already scopes the query correctly, but it is opt-in: the caller must already know the risk exists.

**Why now:** `assert-no-callers` exists specifically to replace human/agent judgement with a deterministic exit code — a delete/move safety gate for a mill batch's `verify:` step. A false positive there is worse than one a reviewer might catch by re-reading the code, because the entire point is to make the re-reading unnecessary. And the build-tag blind spot is load-bearing for exactly the kind of build-tag-separated repo this tool is aimed at, including this one.

## Scope

**In:**

- A `--build-tags <a,b>` flag on all four verbs (`refs`, `definition`, `symbol`, `assert-no-callers`), with a `$QUARRY_BUILD_TAGS` environment fallback.
- A new `initialization_options` field on `registry.Entry`, holding a per-language nested map with a `{{tags}}` placeholder; Go's built-in entry populates it, the other four leave it empty. It is a build-tag template only, never a general static-configuration channel.
- Rendering that map (comma-joined tag substitution) and sending it as `initializationOptions` on the LSP `initialize` request, for both `EnsureServer` strategies and the legacy cold-spawn path.
- A hard error when `--build-tags` is passed for a language whose registry entry's `initialization_options` contains no `{{tags}}` placeholder (absent, empty, and placeholder-free templates all fail identically).
- Folding the normalized tag set into the resolved daemon state directory, so each distinct tag set gets its own supervised daemon, socket, state file, and lock.
- On the native strategy, spawning a private (non-`-remote=auto`) gopls whenever the tag set is non-empty, since the shared native daemon's identity is not a function of the state directory.
- A new typed engine error for "this language's registry entry cannot carry build tags", raised inside the engine's own detect step and re-exported through `quarry/facade.go`.
- A shared build-tag normalization function in `registry`, called by both `internal/cli` (for state-dir keying) and the engine (defensively), exported as `quarry.NormalizeBuildTags`.

## Decisions

### build-tags-cli-surface

- Decision: A per-verb `--build-tags <a,b>` string flag on all four verbs, resolved in the precedence `--build-tags` > `$QUARRY_BUILD_TAGS` > empty.
- Rationale: Matches the existing per-verb `--target-dir` / `--lang` / `--timeout` pattern rather than the root's `--config` / `--state-dir` infrastructure flags — build tags are a query-scoping concern, not process infrastructure. The environment fallback lets a build-tag-separated repo set the tag set once for a whole agent session instead of repeating the flag on every invocation.
- Rejected: A root persistent flag (one definition site, but groups a query flag with infrastructure flags). Per-verb flag with no env fallback (smallest surface; forces repetition). `servers.yaml`-only configuration (makes tags workspace config rather than per-call, and a per-call override is genuinely wanted).

### registry-owns-the-spelling

- Decision: `registry.Entry` gains an `InitializationOptions map[string]any` field (yaml key `initialization_options`) carrying a per-language, YAML-native nested map. Go's built-in entry is `{buildFlags: ["-tags={{tags}}"]}`. The engine deep-copies the map and substitutes the comma-joined tag list into every string value containing the `{{tags}}` placeholder.
- Rationale: This is what issue #2 itself proposes — keep gopls's spelling of the option out of `internal/cli`. A YAML-native nested map avoids stringly-typed JSON embedded in YAML, permits arbitrary nesting, and lets a future language contribute its own shape with no engine-code change. The existing whole-entry-replacement overlay semantics mean adding a field is compatible: an override that omits it simply gets the zero value, consistent with how `pinned_version` / `has_native_daemon` already behave.
- Rejected: Two flat fields (`build_tags_option` + `build_tags_template`) — only expresses a top-level key holding a one-element string list. A single JSON-fragment string field — maximum flexibility, worst readability, parse errors surface late. CLI hard-coding gopls's spelling — one language today, a code change per future language, and explicitly what the issue argues against.

### template-substitution-semantics

- Decision: `initialization_options` is a **build-tag template only**, never a general static-configuration channel. That single rule resolves every case:
  - **Empty tag set → no `initializationOptions` key is sent at all**, whatever the entry carries. The `initialize` request is byte-identical to today's.
  - **Non-empty tag set + a template containing `{{tags}}`** → render and send. Substitution is comma-join-and-replace: the normalized tag set is joined with `,` into one string, and every string value anywhere in the deep-copied map containing `{{tags}}` has the placeholder replaced. No per-tag list expansion. Map keys are never substituted.
  - **Non-empty tag set + no `{{tags}}` anywhere in the template** (including an absent or empty template) → hard error, per `unsupported-language-hard-error`.
- Rationale for refusing a static-configuration reading: treating a placeholder-free template as legitimate static config would mean `--build-tags integration` against such an entry is accepted and silently ignored — the exact silent-ignore failure mode `unsupported-language-hard-error` exists to prevent. That is not a hypothetical: overlay entries whole-replace their built-in counterpart (`registry.go:14-16` and `load.go:55-58`; `docs/servers.yaml.example:1-6`), so an operator `go:` block that edits options and drops the placeholder produces it by default. No built-in entry needs static options, so the general channel would be YAGNI machinery whose only reachable effect is that failure mode.
- Rationale for the empty-tag-set case: `lspclient.go:402` sends no `initializationOptions` today, so both other candidates would silently change the session config of **every untagged Go query** — the overwhelming majority of queries — and would contradict the back-compat promise `daemon-keyed-by-tag-set` and `native-path-private-spawn` both make ("byte-identical to today's", "today's argv byte for byte"). An empty `-tags=` is also not obviously inert to gopls, and an empty `buildFlags` list is not obviously equivalent to an absent one; neither is worth depending on when sending nothing is available and provably unchanged. This makes the empty-tag-set path uniformly a no-op across all three mechanisms — no `initializationOptions`, no state-dir segment, no native argv change — which is the property the back-compat tests assert.
- Rationale: YAGNI. rust-analyzer's `cargo.features: [a, b]` shape is the only known case needing per-tag expansion, and no non-Go language gets a template in this task. Implementing expansion now would be designing for a hypothetical.
- Rejected: Per-tag list expansion (a `{{tag}}` singular placeholder expanding its containing list element once per tag) — real machinery for zero current consumers.

### unsupported-language-hard-error

- Decision: Passing `--build-tags` (or having `$QUARRY_BUILD_TAGS` set non-empty) for a language whose resolved registry entry has **no `{{tags}}` occurrence anywhere in its `initialization_options`** is a hard error, raised **before** the language server is spawned. The predicate is the placeholder's absence, not the map's emptiness: an absent template, an empty template, and a non-empty template that never mentions `{{tags}}` are all cases where the tag set provably cannot reach the server, and all three must fail identically rather than one of them silently ignoring the flag. The check lives **in the engine**, in `query`'s own pipeline immediately after `registry.DetectLanguage` resolves the entry and before `acquireConnection` — that is, inside `lookup` (`internal/quarryengine/query/refs.go`), inside `Symbol`'s equivalent step, and inside the new verification entry point. It is a new typed error (`ErrBuildTagsUnsupported`, carrying the language name) declared in `internal/quarryengine/errors.go` alongside the existing typed errors and re-exported from `quarry/facade.go` with its sentinel, following the established pattern of `ErrResolverUnsupported`. `internal/cli` maps it to the standard `output.Err` envelope with exit 1, exactly as it maps every other engine error today. Message shape: `quarry: --build-tags is not supported for language "python" (its registry entry's initialization_options has no {{tags}} placeholder)` — the wording names the placeholder rather than the field's presence, so the operator who dropped it from an overlay entry is told what to put back.
- Rationale: A silently-ignored precision flag is precisely the failure mode issue #2 is about — the caller believes they have widened the view and they have not. The flag must either work or fail loudly. Raising it before spawn avoids paying a server launch for a query that cannot honour its own scoping.
- Rejected: Warn on stderr and proceed — the JSON-envelope contract makes stderr warnings easy for an agent caller to miss entirely. Silent ignore — no new failure mode and no signal.
- Note on the engine-side placement: the error must name the language, so it cannot be raised before detection. `internal/cli` does not call `DetectLanguage` today — only `quarry/facade.go:104` re-exports it — so siting the check in the CLI would require a second, duplicate detection pass with its own `ErrNoLanguage` surface. Putting it in the engine keeps detection single-pass and keeps the CLI in its existing role of mapping typed engine errors to envelopes. Its tests are therefore `query`-package hermetic tests, not `internal/cli` tests.
- Note on the environment fallback: `$QUARRY_BUILD_TAGS` set globally in a shell and then running a query against a python project hard-errors. This is accepted as correct under the "must fail loudly" rationale, and must be documented in `README.md`'s configuration section.

### daemon-keyed-by-tag-set

- Decision: The normalized tag set becomes part of the resolved daemon state directory. When the tag set is empty, the resolved path is byte-identical to today's (no new segment, no re-keying, existing daemons keep working). When it is non-empty, a `tags-<hex>` segment is appended to the resolved leaf directory — applied uniformly at all three precedence tiers, including the explicit `--state-dir` / `$QUARRY_STATE_DIR` tiers, which bypass `workspaceKey` entirely today. `<hex>` is the first 6 bytes of the SHA-256 digest of the normalized tag set joined with `,`, hex-encoded to 12 characters — the same hash and truncation `workspaceKey` already uses (`internal/cli/paths.go:63-64`), so there is one hashing convention in this file rather than two.
- Rationale: `initializationOptions` are nominally per-session, so one daemon might serve two tag sets correctly — but that is an unverified assumption about gopls's internals, and a shared cache re-indexing on every tag flip is a latency cliff. A distinct key makes the behaviour explicit instead of implementation-dependent. Applying it at every tier matters because an operator who pins `--state-dir` would otherwise silently collide two tag sets on one socket, which is exactly the case the decision exists to prevent.
- Rejected: One daemon per workspace regardless of tags (ties correctness to unverified gopls behaviour). Recording the tag set in `daemon.json` and respawning on mismatch (one daemon at a time, but thrashes when callers alternate tag sets — and an agent alternating tagged and untagged queries is the expected usage).
- Accepted cost: an agent alternating tagged and untagged queries leaves **two** gopls daemons concurrently resident, each having indexed the whole module, and each held for the full `daemonIdleTimeout` of 10 minutes (`internal/quarryengine/daemon/ensureserver.go:139`) after its last use. That is roughly double the memory and double the initial indexing work of today's single-daemon steady state. This is accepted deliberately: it is the price of not depending on gopls's per-session view isolation, and it is bounded (one daemon per distinct tag set actually used, reclaimed on idle) rather than unbounded. The rejected respawn-on-mismatch alternative trades this steady-state cost for repeated cold-start latency, which is worse for the alternating usage pattern that motivates the decision.

### native-path-private-spawn

- Decision: When the normalized tag set is non-empty, the native strategy spawns a **private** gopls — `nativeArgv` omits `-remote=auto` and its `-remote.listen.timeout` companion — instead of joining the shared auto-daemon. With an empty tag set, `nativeArgv` is unchanged and the shared daemon is used exactly as today.
- Rationale: `daemon-keyed-by-tag-set` partitions only the *supervised* strategy, because the `tags-<hex>` segment lives in the state directory and the supervised daemon's socket path is derived from it. The native strategy's daemon identity is not a function of `stateDir` at all — `nativeArgv` (`internal/quarryengine/daemon/ensureserver.go:146`) hands gopls `-remote=auto`, and gopls derives that shared daemon's address itself. So on the native path the state-dir segment partitions nothing, and two tag sets would land in one shared daemon, reinstating exactly the unverified per-session-view assumption `daemon-keyed-by-tag-set` exists to avoid. This is not a rare edge case: `EnsureServer` (`ensureserver.go:67-73`) falls back to `ensureNative` on *any* `ensureSupervised` failure on every platform, and on windows the supervised strategy is unavailable outright (it hard-codes a Unix domain socket), making native the only path there. A private spawn is correct by construction — an unshared process cannot mix tag sets with anyone — and needs no knowledge of gopls internals.
- Cost, accepted: a tagged query on the native path pays a cold gopls start and gets no cross-invocation reuse. The cost is isolated to tagged queries; untagged queries keep today's shared-daemon behaviour byte for byte. On linux this is reached only when supervised spawn fails; on windows it is the normal path for tagged queries, and must be documented in `README.md`'s "Windows: native strategy only" section.
- Cost, accepted (batch-mode amplification): the cost above is **per engine call, not per process invocation**. `refs`, `definition`, and `symbol` accept N positional arguments and make one independent engine call per argument inside `runBatch` (`internal/cli/cli.go:189-199`, `:331`, `:432` — each calls `buildOptions` followed by its own `quarry.References` / `Definition` / `Symbol`), and each of those runs a full `acquireConnection` → `teardownConnection` cycle. So an N-symbol batch on the native path with a non-empty tag set pays **N** cold gopls starts within one invocation, each indexing the whole module — not one. On windows, where native is the only path, that is the normal cost of a tagged batch query. This is accepted for this task rather than fixed: sharing one connection across a batch means an engine-level batch entry point, which is a substantially larger change than either issue asks for, and it would want to serve the supervised path too rather than being bolted onto the native fallback. It is recorded here so the trade is explicit, not discovered later.
- Follow-up: file one GitHub issue for batch-mode connection reuse — an N-symbol batch running N independent connection cycles is wasteful on every path, and merely pathological rather than merely wasteful on native-plus-tags. This task does not fix it.
- Rejected: Accepting shared-daemon tag mixing and documenting it as a known limitation — reintroduces the rejected assumption on the one platform where native is the only path, so it is a correctness problem rather than a documented rough edge. Hard-erroring when tags are non-empty and the native path is reached — honest and loud, but makes `--build-tags` unusable on windows entirely, defeating the point of issue #2 for those users. Shipping tag support supervised-only and filing the native gap separately — smallest change, but leaves windows silently wrong until a follow-up lands, and silent wrongness is the failure mode both issues are about.

### tag-set-normalization

- Decision: The raw flag/env string is split on `,`, each element trimmed of surrounding whitespace, empty elements dropped, duplicates removed, and the remainder sorted lexicographically. The normalized set is what feeds both the `{{tags}}` substitution and the state-dir key. A raw value that normalizes to the empty set is treated as "no build tags" everywhere, including the `unsupported-language-hard-error` check — so `--build-tags ""` and `--build-tags " , "` are not errors on python.
- Rationale: Sorting and deduplicating make the state-dir key a function of the tag *set*, not of the argument's spelling, so `--build-tags b,a` and `--build-tags a,b` reuse one daemon instead of two. Dropping empties makes trailing commas harmless. Treating an empty normalization as absent keeps the back-compat path (`empty set → unchanged state dir`) coherent with the error check.
- Where it lives, and who calls it: normalization is a function in **`registry`**, next to the template renderer that consumes its output, exported through the facade as `quarry.NormalizeBuildTags` (bringing the facade identifier count to **33**). Both layers call it, and neither may assume the other did. `internal/cli` normalizes the flag/env value because it needs the result for state-dir keying before the engine is ever entered. The engine **re-normalizes defensively** on entry, because `Options.BuildTags` is public via `quarry.Options` and a non-CLI caller passing `[""]` or `["b","a"]` would otherwise bypass the empty-set no-op and reach the hard-error predicate, which is specified over normalized tags. Normalization is idempotent, so the second pass is free. This deliberately differs from `Options.StateDir`, which is documented as entirely the caller's obligation (`internal/quarryengine/query/refs.go:76-79`): a wrong `StateDir` fails loudly, whereas an unnormalized tag set fails silently by changing which daemon is used and whether the flag is honoured at all.
- Rejected: Preserving caller order (would key two daemons for one logical set). Rejecting malformed input (a trailing comma is not worth an error).

### verification-over-scope-heuristics

- Decision: Fix the interface-method false positives with a definition-verification filter, not a scope heuristic. For each candidate reference returned by `textDocument/references`, issue `textDocument/definition` at that reference's position and keep the reference only if its definition resolves to the symbol's own declaration.
- Rationale: It is exact rather than heuristic, and it carries no false-negative risk from an invented scope. It operates at the LSP level, so it generalizes past Go without per-language knowledge. It also handles the case the alternatives cannot: a genuinely cross-package interface method whose real callers legitimately live outside the declaring package.
- Rejected: Kind-gated auto-scope (detect via `documentSymbol` that the declaration's enclosing symbol is an interface, then default the scope to the declaring package directory) — cheap, but silently drops a cross-package interface method's real callers, a false negative in a safety gate. Defaulting `--within` to `--target-dir` for every symbol kind, with a `--workspace-wide` opt-out (issue #1's own "open question") — trivial, but for plain functions it converts today's false positives into false negatives, so the gate would pass with real callers outstanding. Warn-only, telling the caller to pass `--within` — zero risk, leaves the default unsafe, which is what the issue objects to.
- The declaration set is widened by `textDocument/implementation`. gopls unifies an interface method's references with every implementer's into one set (`docs/scout-multilang.md:140`, reproducing loomyard finding #008), and that unification runs in **both** directions. Verifying against the definition result alone is therefore safe in one direction and a fail-open in the other:
  - Query is the **interface method**: references include call sites on concrete types. Their definitions resolve to the concrete methods, so they are dropped. Correct — deleting the interface method does not break a call made directly on a concrete type.
  - Query is the **concrete method**: references include interface-dispatch call sites. Their definitions resolve to the *interface's* declaration, not the concrete method's, so verification against the definition set alone would drop them — and `assert-no-callers` would go green on a delete that breaks interface satisfaction and therefore the build. That is a false negative in a safety gate, the one failure class this whole design exists to avoid.
- Decision: the declaration set is `textDocument/definition` at the query position **∪ `textDocument/implementation` at the query position**, and a reference is kept if its own definition intersects that union. The widening is symmetric — no attempt is made to detect which side of the relation the queried symbol sits on — because a safety gate must fail closed, and an unnecessarily kept reference costs a re-read while a wrongly dropped one costs a broken build. It costs one extra LSP call at the declaration, not one per reference.
- Precision impact of the widening, and why it is small: the noise issue #1 measures is *unrelated, structurally-identical* interfaces (29 of 31 reported callers belonged to two independently declared `clock` interfaces in other packages). Those are not in any implements relation with the queried symbol, so `textDocument/implementation` does not re-admit them. What the widening re-admits is genuine implementers of the actual interface — related code a caller checking a delete should see.
- Requires: a new `Implementation` method on `lsp.Client` (`textDocument/implementation`), plus an `implementationProvider` capability accessor alongside the existing `SupportsWorkspaceSymbol` / `SupportsDocumentSymbol`. If the server does not advertise `implementationProvider`, or the implementation call errors, verification is **skipped entirely** and every reference is kept — the same fail-closed rule `fail-closed-verification` applies to a missing declaration set, for the same reason: a partially-computed declaration set can only cause false negatives.
- Rejected for this widening: detecting whether the queried symbol is an interface method or a concrete method and widening only in the "implements" direction. More precise in principle, but it makes the gate's correctness depend on a kind-detection heuristic — exactly the kind of dependency `verification-over-scope-heuristics` rejects — and the extra precision it buys is limited to genuine implementers, which are legitimately relevant to a delete check.

### verification-scoped-to-assert-no-callers

- Decision: Verification applies to `assert-no-callers` only. It is on by default, and `--no-verify` disables it. `refs`, `definition`, and `symbol` are unchanged and gain no verification flag.
- Rationale: `assert-no-callers` is the deterministic gate where a false positive actually blocks something. `refs` is a listing a human or agent reads and filters; over-reporting there is recoverable, and N extra round trips would be visible latency for no gain.
- Rejected: All four verbs default-on (consistent, at a latency cost on the read-only verbs). All verbs default-off with a `--verify` opt-in (no regression risk, but leaves the complained-about default exactly as it is).

### fail-closed-verification

- Decision (per-reference): A reference is dropped only when verification positively disproves it — that is, the definition call succeeded and returned a location set that does not intersect the declaration set. A reference whose definition call errors, times out, or returns an empty result is **kept** as a violation. Verification never aborts the command.
- Decision (declaration side): If the declaration-side `textDocument/definition` errors **or returns an empty location set**, or the `textDocument/implementation` half of the declaration set is unavailable (capability unadvertised, or the call errored), verification is **skipped entirely** and every reference is kept. Verification only ever subtracts when there is a declaration to verify against; it is never applied against an empty declaration set.
- Rationale: Fail-closed is mandatory for a safety gate. A degraded or flaky server must never be able to turn the gate green by quietly failing its own verification step. Keeping unverifiable references preserves today's behaviour for exactly the references verification could not improve on. The declaration-side rule is not a redundant restatement of the per-reference one: an empty declaration set is a *silent success*, not an error — `lookup` (`internal/quarryengine/query/refs.go:214`) returns `toSortedReferences(locations)` with a nil error on an empty location list — and no reference can intersect an empty set, so applying verification against it would drop **every** reference and exit 0 with an empty `callers` list. That is the exact fail-open this decision exists to prevent, and it inverts today's behaviour, where an empty `declRefs` makes every reference a violation (`internal/cli/cli.go:637`). Skipping verification preserves that behaviour byte for byte in the degraded case.
- Rejected: Dropping errored/empty per-reference verifications (quieter, but a flaky server silently weakens the gate). Aborting the whole command on any verification error (one hiccup on one reference kills an otherwise-complete answer). Treating an empty declaration set as a hard error with an error envelope (loud, but converts a case that today yields a usable violation report into a failure — and the `violation` field is the only thing distinguishing the two exit-1 meanings, so the caller loses information). Applying verification against the empty set (the fail-open bug; recorded so the rejection is explicit).

### declaration-match-is-positional

- Decision: The declaration set is the union of `textDocument/definition` and `textDocument/implementation` at the resolved query position (see `verification-over-scope-heuristics` for why the implementation half is required), and a reference matches it when its own definition result shares at least one location with that union by exact `(file, line, character)` equality. All comparisons happen in LSP wire coordinates (0-based line, UTF-16 character) before any conversion to the public 1-based `Reference` type.
- Rationale: File-level matching would conflate two same-named methods declared in one file. Comparing in wire coordinates avoids the byte-column-vs-UTF-16-column hazard the existing code already documents at `internal/cli/cli.go`'s `declRefs` comment: `Position.Character` is a 1-based *byte* column, which coincides with the UTF-16 column only on a pure-ASCII line.
- Rejected: File-level match (cheaper, conflates same-file same-name declarations). Comparing after conversion to the public `Reference` type (works, but reintroduces a coordinate-system conversion in the middle of a correctness-critical comparison for no benefit).

### one-connection-verification-entry-point

- Decision: Verification is implemented as a new engine-level entry point named **`query.Callers`**, re-exported as **`quarry.Callers`**, that performs, on **one** connection: resolve position → `textDocument/definition` (the declaration set) → `textDocument/references` → per-reference `textDocument/definition` → filter. It is re-exported through `quarry/facade.go`, and `internal/cli`'s `assert-no-callers` calls it instead of its current two separate `quarry.Definition` + `quarry.References` calls.
- Return contract: `(references []Reference, declaration []Reference, err error)` — the filtered reference set and the declaration set, both already converted to the public 1-based `Reference` type and both sorted by the existing `toSortedReferences` ordering. The declaration set is returned because verification deliberately *keeps* the declaration site (a declaration's own definition trivially matches the declaration set), so `internal/cli`'s `filterUnexpectedCallers` (`cli.go:671`) still needs it to exclude that site — exactly as it uses today's `declRefs`. A tuple rather than a result struct: two values plus an error is idiomatic Go here, and promoting it to a struct later is a mechanical change if a third value ever appears.
- `--no-verify` takes the same entry point with verification disabled, via **`Options.SkipVerification bool`** — negative polarity deliberately, so the zero value means "verify". `query.Options` is re-exported verbatim as the public `quarry.Options` (`quarry/facade.go:41`), and a `Verify bool` would make the fail-open state the struct's zero value for every non-CLI caller, which inverts this task's entire posture. One code path serves both modes, so there is no verify/no-verify pair of pipelines to keep manually in sync, and `--no-verify` becomes exactly today's behaviour with one fewer connection cycle.
- Rationale: `assert-no-callers` today makes two top-level engine calls, each of which runs the whole `acquireConnection` → `teardownConnection` cycle independently (`internal/quarryengine/query/refs.go`'s `lookup`). Adding N more top-level `Definition` calls would mean N more connect/initialize cycles, which is not viable. Consolidating also removes one of the two existing connection cycles, so the verified path is cheaper than today's unverified one in connection terms.
- Rejected: Calling `quarry.Definition` N times from the CLI (N connection cycles). Exposing the raw `*lsp.Client` through the facade so the CLI can drive it (breaks the engine/CLI layering the package comments establish, and `internal/quarryengine/layering_test.go` / `seam_enforcement_test.go` exist to enforce that boundary). Returning a `CallersResult` struct instead of a tuple (same content, YAGNI at two fields, one more facade identifier to justify). Having the entry point apply the declaration exclusion and return only violations (fewest moving parts, but moves `--except` / `--within` semantics into the engine, which is the layering rule `layering_test.go` enforces and this task's whole architecture rests on). Keeping today's two `quarry.Definition` + `quarry.References` calls for the `--no-verify` path only (two pipelines to keep in sync by hand, and the escape hatch would stop sharing a connection for no benefit).
- Note: `quarry/facade.go`'s doc comment (`quarry/facade.go:8-9`) currently states it re-exports "exactly the 29 identifiers this package exported before the engine-repackage move: no more, no less." This task adds exactly four: `Callers` (the new entry point), `ErrBuildTagsUnsupported` (the typed error from `unsupported-language-hard-error`), `ErrBuildTagsUnsupportedSentinel` (its sentinel, following the existing pairing convention for every other typed error in that file), and `NormalizeBuildTags` (needed by `internal/cli` for state-dir keying, per `tag-set-normalization`). The count becomes **33**, and the doc comment must be rewritten to say so rather than left stale — the sentence's whole value is that it is checkable.

### sequential-verification

- Decision: Per-reference definition calls run **strictly sequentially**, and the whole verification phase is bracketed by a single `context.WithTimeout(ctx, opts.Timeout)` deadline — one deadline for the phase, not one per call — matching how `lookup` already brackets each of its phases. A verification phase that hits its deadline yields kept (unverified) references for whatever remains, per `fail-closed-verification`, and is never an error.
- Decision (deadline vs teardown): a verification-phase deadline **does** set `lookup`'s `timedOut` flag, **while still returning a successful result** with the unverified references kept. These are independent concerns and must not be collapsed: `timedOut` answers "might this server be stalled?" and governs disposal, while the return value answers "is this answer usable?" and is governed by `fail-closed-verification`. Setting the flag is right because it is the pipeline's existing, uniform way to say "this connection may be wedged"; deciding what that *means* is `teardownConnection`'s job, and it already differs per `ConnKind`. Returning `ErrServerTimeout` instead would be consistent with the other phases but would turn a recoverable degradation into a failed gate, contradicting fail-closed. This is the one place in the pipeline where `timedOut` is set on a non-error return, and it must be commented as such at the call site.
- Consequence per `ConnKind` (the flag does **not** mean "hard-kill" everywhere): `teardownConnection` (`internal/quarryengine/query/refs.go:137-157`) hard-kills on `timedOut` only for `ConnKindNative` and `ConnKindLegacy`. For `ConnKindSupervised` — which is Go's *primary* strategy, returned whenever `ensureSupervised` succeeds (`ensureserver.go:67-70`) — it returns immediately with no kill and no close, by design: the daemon is meant to outlive this call and serve other callers, and a query path has no supervisory authority to kill it. So on the dominant Go path a verification deadline changes nothing about teardown; setting `timedOut` matters for the native and legacy paths, where the graceful `Close()` handshake against a stalled server is the documented re-block hazard (`refs.go:117-121`).
- A possibly-stalled *supervised* daemon needs no action here, and this task adds none: `ensureSupervised` already owns wedged-daemon detection and escalation on the next call through its state-file staleness check and re-dial-under-lock path. Duplicating that judgement in a query-path timeout handler would be the wrong seam and would risk killing a daemon that is merely busy.
- Rationale: `lsp.Client` is **single-flight and cannot support concurrent calls**. `Call` (`internal/quarryengine/lsp/lspclient.go:330`) increments `c.nextID` with no synchronization, `writeMessage` (`:263`) holds no write mutex so two concurrent frames could interleave on the wire, and `Call`'s response loop reads a single shared `c.incoming` channel and silently discards any message whose ID is not its own — with no pending-request registry, two concurrent callers would consume and drop each other's responses. Concurrency here is therefore not a tuning choice but a transport change. Sequentially, 31 references against a warm daemon complete in well under a second, and the single phase deadline means the worst case is bounded by `--timeout`, not by N × timeout. The performance premise that motivated concurrency does not survive contact with the transport, and the transport is correctness-critical for every verb.
- Rejected: Bounded concurrency (8 in flight) — unsafe against the current transport, as above. Giving `lsp.Client` a pending-request registry plus a write mutex and then using concurrency — the right long-term fix, but it expands this task's scope into the transport every verb depends on in order to save a fraction of a second on one verb. Concurrency plus a hard cap on how many references get verified (bounds cost, reintroduces an unverified blind spot exactly where the noise is worst).
- Follow-up: file one GitHub issue recording `lsp.Client`'s single-flight limitation — unsynchronized `nextID`, no write mutex, no pending-request map — so the constraint is written down rather than rediscovered. This task does not fix it.

### filter-ordering

- Decision: The filters compose in a fixed order: verification first, then `--within`, then `--except`, then the declaration-site exclusion that `filterUnexpectedCallers` already performs. `--within` and `--except` keep their current semantics unchanged; `--no-verify` restores exactly today's pipeline.
- Rationale: Verification is a precision correction on the raw reference set, so it belongs closest to the source. `--within` is already documented as applying "before `--except` is applied" (`internal/cli/cli.go`'s `assert-no-callers` Long help), and that documented relationship is preserved.
- No restructuring is implied by the four-stage phrasing: the last two stages are one existing function. `filterUnexpectedCallers` (`internal/cli/cli.go:671-688`) applies `--except` and the declaration exclusion in a single pass, and they are order-independent anyway since both are removals. It stays exactly as it is; only verification is new, inserted ahead of `--within`.
- Rejected: Verification after `--within` (equivalent result, but makes the `--within` help text's ordering claim harder to state). Making `--within` and verification mutually exclusive (they are independent and composing them is coherent — a caller may want both).

## Technical context

**The `initialize` gap.** `lsp.Client.Initialize(ctx, rootURI)` at `internal/quarryengine/lsp/lspclient.go:402` sends `processId`, `rootUri`, and `capabilities`, and nothing else. Its two callers are `internal/quarryengine/daemon/ensureserver.go:94` (inside `finalizeConnection`, serving both the supervised and native strategies) and `internal/quarryengine/query/refs.go:116` (the legacy cold-spawn path for languages with `HasNativeDaemon == false`). Both must pass the rendered options, so the signature change touches both call sites. `initializationOptions` ride the per-session `initialize` request, so the `-remote=auto` native proxy and the `-listen=unix;...` supervised daemon both receive them with no protocol-level change.

**Where the option value lands.** For gopls the key is `buildFlags`, holding an argv-style list — `{"buildFlags": ["-tags=integration,smoke"]}`. gopls accepts this flat spelling as well as the newer nested `build.buildFlags`; the flat form is what the Go built-in entry should carry, and the exact spelling should be verified against the pinned `v0.23.0` (`registry.go`'s Go entry `PinnedVersion`) during implementation.

**Options plumbing.** `query.Options` (`internal/quarryengine/query/refs.go:74`) is the engine's config struct and is re-exported verbatim as `quarry.Options` via a type alias in `quarry/facade.go`. Adding a `BuildTags []string` (normalized) field there is the natural carrier and does not disturb the facade's identifier count, which counts identifiers rather than struct fields. `buildOptions` at `internal/cli/cli.go:492` is the single construction site for all four verbs.

**Registry shape.** `registry.Entry` (`internal/quarryengine/registry/registry.go`) already carries Go-only optional fields (`PinnedVersion`, `HasNativeDaemon`) with explicit yaml tags, so `InitializationOptions map[string]any` with tag `initialization_options` follows an established pattern. Note that `LoadRegistry` (`load.go`) decodes with `yaml.Decoder.KnownFields(true)`: adding the field is what makes it *permissible* in an operator's `servers.yaml`, and until then such a key is a loud error. `validateEntry` currently enforces non-empty markers / valid match / non-empty command / non-empty install hint; the new field is optional and must not be added to those required checks. Overlay semantics are whole-entry replacement, so an operator's `go:` block that omits `initialization_options` loses the built-in template — the same already-documented sharp edge that applies to `pinned_version`, and `docs/servers.yaml.example`'s header comment already warns about it.

**State-dir keying.** `workspaceKey` (`internal/cli/paths.go:55`) is `filepath.Base(targetDir) + "-" + hex(sha256(clean(abs))[:6])`. `resolveStateDir` (same file) picks `--state-dir`, then `$QUARRY_STATE_DIR`, then `filepath.Join(userCacheDir(), "quarry", workspaceKey(targetDir))` — the first two tiers bypass `workspaceKey` entirely, which is why the `tags-<hex>` segment is specified as applying to the *resolved* leaf rather than being folded into `workspaceKey`. `resolveContext` at `internal/cli/cli.go:462` is the single call site and needs the normalized tag set threaded in. `DaemonStateFile` / `DaemonLock` join their own `<lang>` segment below the leaf, so appending a segment to the leaf keeps the daemon-side layout unchanged.

**assert-no-callers today.** `assertNoCallersCommand` at `internal/cli/cli.go:508` already calls `quarry.Definition` before `quarry.References`, specifically so the declaration site can be excluded in matching coordinate systems — its inline comment explains why building a `Reference` from a caller-supplied `Position` would be wrong. That reasoning carries straight over to the new entry point: the declaration set must come from a real `textDocument/definition`, not from the query position. `filterWithin` / `isWithinDir` / `filterUnexpectedCallers` (`cli.go:670`–`730`) stay as they are.

**The `lookup` pipeline.** `internal/quarryengine/query/refs.go`'s `lookup` takes a single `lspCall` closure and therefore expresses exactly one LSP call per connection. The new entry point needs several calls on one connection, so `lookup` needs generalizing — either a sibling that hands the resolved `(client, fileURI, pos)` to a caller-supplied closure, or a variant `lspCall` signature. Whichever shape is chosen, `lookup`'s existing invariants must be preserved: the `timedOut` flag is captured by reference by the deferred `teardownConnection` precisely because a later phase can still set it, and `teardownConnection`'s `ConnKindSupervised` branch must keep returning without any shutdown handshake or kill.

**The transport is single-flight.** `lsp.Client.Call` (`internal/quarryengine/lsp/lspclient.go:330`) is safe for exactly one in-flight request at a time. It increments the unexported `nextID` field (`:132`, `:341`) without synchronization; `writeMessage` (`:263`) takes no write lock; and the response loop (`:353`) selects on one shared `c.incoming` channel, returning only on an ID match and silently discarding everything else — there is no pending-request map to route a response back to the right caller. Any change that introduces concurrent `Call`s must first add that registry and a write mutex. This is why `sequential-verification` is sequential, and it constrains any future work in this area.

**Native vs supervised daemon identity.** These are partitioned by different mechanisms and only one of them is under quarry's control via `stateDir`. The supervised strategy derives its socket path from the state directory (`ensureserver.go`'s `ensureSupervised`, `socketPath := filepath.Join(filepath.Dir(statePath), "daemon.sock")`), so the `tags-<hex>` segment partitions it. The native strategy hands gopls `-remote=auto` (`nativeArgv`, `:146`) and gopls picks the shared daemon address itself, so no state-dir change affects it — hence `native-path-private-spawn`. `EnsureServer` (`:67-73`) falls through from supervised to native on *any* supervised error, on every platform; windows has no supervised path at all.

**Layering enforcement.** `internal/quarryengine/layering_test.go` and `internal/quarryengine/seam_enforcement_test.go` encode the five-package DAG (root leaf, `lsp`, `registry`, `daemon`, `query`). Anything added must respect it — in particular, `internal/cli` must not reach past the `quarry/` facade. Template rendering is placed in **`registry`**: both `registry` and `query` are legal under the DAG, and `registry` wins because it already declares `Entry` and owns the `initialization_options` field's meaning, including the `{{tags}}` contract and the `validateEntry` conventions around it. Keeping the field's shape and its interpretation in one package means the `{{tags}}` rule has a single home rather than being declared in one package and enforced in another. `query` calls the renderer; `lsp` never sees it, receiving only the finished map.

**Test-tier convention.** Live tests are `//go:build lsp`-tagged in their own `*_integration_test.go` / `*_lsp_test.go` files, skip via `exec.LookPath("gopls")` when the binary is absent, and are run with `go test -tags lsp ./...`. `internal/quarryengine/query/refs_integration_test.go` is the closest model for a new query-level live test, and `internal/quarryengine/daemon/daemontest` provides the shared helpers. Note the pleasing recursion: the build-tag live test needs a fixture module containing a `//go:build`-tagged file, inside a repo whose own live tests are `//go:build lsp`-tagged.

**Prior evidence.** `docs/scout-multilang.md:115`–`136` carries the quantified build-tag gap and the analysis that ruled out a workspace-load race before attributing it to build tags. `docs/scout-agent-usage-findings.md` and `docs/scout-vs-grep.md` carry the interface-conflation measurement. These are the reference numbers any new benchmark should be compared against.

## Testing

No `CONSTRAINTS.md` exists at the hub root.

**Hermetic tier (`go test ./...`, no external binary).** These are the TDD candidates — every one is a pure function over in-memory values:

- Tag normalization (`registry`, called from both layers): split, trim, drop empties, dedupe, sort; and idempotence, since the engine re-normalizes what the CLI already normalized. Scenarios: `"b,a"` and `"a,b"` normalize identically; `""`, `","`, `" , "` all normalize to the empty set; `"a,,b, a "` yields `[a b]`.
- Template rendering (`registry`): substitution into a nested map. Scenarios: nested map with `{{tags}}` in a list element renders correctly; the source entry map is not mutated (deep copy); map *keys* are never substituted; a non-empty tag set against a placeholder-free template yields `ErrBuildTagsUnsupported` rather than a silently-unsubstituted map; **an empty tag set against a template-bearing entry produces no `initializationOptions` key at all** (not `-tags=`, not an empty list), so the `initialize` request is byte-identical to today's — the back-compat assertion for this mechanism, and the counterpart of the state-dir and `nativeArgv` no-op assertions below.
- Unsupported-language error (`query`, not `internal/cli` — see `unsupported-language-hard-error`'s placement note): non-empty normalized tags plus an entry with empty `initialization_options` yields `ErrBuildTagsUnsupported`, the error names the language, and it is raised before any connection is acquired. Complement: an empty normalization against such an entry is *not* an error. A separate `internal/cli` test covers only the mapping of that typed error to the `output.Err` envelope with exit 1, matching how the other typed errors are already tested there.
- State-dir keying (`internal/cli`): empty tag set yields byte-identical paths to today at all three precedence tiers (this is the back-compat assertion and should be written first); a non-empty set yields distinct paths at all three tiers, including explicit `--state-dir`; `b,a` and `a,b` yield the same path; the `tags-<hex>` segment is 12 hex characters, matching `workspaceKey`'s own truncation.
- `nativeArgv` (`daemon`): an empty tag set produces today's argv byte for byte, including `-remote=auto` and `-remote.listen.timeout`; a non-empty tag set produces an argv with neither flag. `nativeArgv` is already factored out specifically to be unit-testable without spawning a process, so this needs no new seam.
- Registry decode (`registry`): a `servers.yaml` carrying `initialization_options` decodes without tripping `KnownFields(true)`; an entry omitting it validates fine (the field is optional); built-in Go carries the template and the other four do not. Also assert the overlay hazard the hard-error predicate exists for: a `go:` block that whole-replaces the built-in and drops the `{{tags}}` placeholder produces `ErrBuildTagsUnsupported` on a tagged query, not a silently ignored flag.
- The verification filter as a pure function over `(declarationLocations, references, perReferenceDefinitionResults)`. Scenarios, mirroring issue #1's measurement: a reference whose definition matches the declaration is kept; one whose definition points elsewhere is dropped; one whose definition call errored is kept (fail-closed); one whose definition returned empty is kept (fail-closed); exact-position matching distinguishes two same-named declarations in one file. **Both directions of the interface relation must be pinned, not just one:** querying the interface method, a call site on a concrete type is dropped (deleting the interface method does not break it); querying the concrete method, an interface-dispatch call site is **kept** because the implementation half of the declaration set matches it — the false negative from round 5, and the scenario most worth writing first. A reference matching neither half is dropped in both directions, which is what preserves issue #1's 31→2 result, since unrelated structurally-identical interfaces are in no implements relation with the queried symbol. Also: an unavailable `textDocument/implementation` (capability unadvertised, or call errored) skips verification entirely and keeps every reference.
- Filter ordering, split across the two tiers it actually spans. Verification now lives in the engine (`one-connection-verification-entry-point`), and `internal/cli` calls `quarry.Callers` as a direct package-level call with no injection seam (`cli.go:608`, `:614`), so no `internal/cli` test can observe the verification step. Therefore: `internal/cli` asserts only the three CLI-side filters it can reach — `--within` → `--except` → declaration exclusion — over a hand-built reference slice; and the engine test asserts that `query.Callers` returns already-verified references, i.e. that verification precedes everything the CLI does. `--no-verify` reproducing today's CLI-side pipeline exactly is an `internal/cli` assertion.
- `query.Callers`'s return contract (`query`): the declaration set comes back alongside the filtered references, is non-empty for a resolvable symbol, and still contains the declaration site after verification has run — the property `filterUnexpectedCallers` depends on.
- Declaration-side degradation, the fail-open guard — the single most important test in the task, since the failure it guards against is silent. It needs both tiers, because no single package can observe the whole chain. In `query`: an empty declaration set leaves every reference in place rather than dropping all of them, and an errored declaration call does the same. This requires a hermetic seam — a `callersFromClient` helper taking an already-built `*lsp.Client`, exactly mirroring the existing `symbolFromClient` (`internal/quarryengine/query/symbol.go`, driven directly by `symbol_test.go` against a hand-built client rather than through the full pipeline). In `internal/cli`: given a non-empty reference set and an empty declaration set, `assert-no-callers` emits a violation report with exit 1, never exit 0 with an empty `callers` list.
- Verification deadline (`query`): hitting the phase deadline returns a successful result with the remaining references kept **and** sets the `timedOut` flag. Both halves need asserting; testing only the return value would let the teardown regression through. Assert the flag's effect per `ConnKind` — hard-kill for `ConnKindNative` / `ConnKindLegacy`, and no kill and no close for `ConnKindSupervised`, which is the dominant Go path and where the flag is deliberately inert.

**Live tier (`go test -tags lsp ./...`, real gopls on `$PATH`).** Two end-to-end tests, each on its own fixture module, each guarded by `exec.LookPath("gopls")`:

- Build-tag visibility: a fixture module with a symbol referenced from both an untagged file and a `//go:build sometag`-constrained file. Assert the tagged reference is absent without `--build-tags` and present with `--build-tags sometag`. This is the one thing a fake server cannot reproduce, since it is gopls's own view-loading behaviour.
- Interface conflation: a fixture module with two structurally-identical local interfaces in different packages, each with its own callers, reproducing the `clock` shape from issue #1. ## Q&A log

- **Q:** How do build tags reach the CLI — per-verb flag, root persistent flag, per-verb only, or `servers.yaml` only? **A:** Per-verb `--build-tags` on all four verbs plus a `$QUARRY_BUILD_TAGS` fallback; it matches the existing `--target-dir`/`--lang` pattern and the env var avoids repeating the flag across an agent session.
- **Q:** Who owns the per-language spelling of the option — registry entry, CLI hard-code, or a generic passthrough? **A:** The registry entry, which is what issue #2 itself proposes; it keeps gopls-specific spelling out of `internal/cli` and is the right home for per-language variation.
- **Q:** Should the daemon be keyed by the build-tag set? **A:** Yes. Relying on gopls keeping per-session views separate is an unverified assumption; an explicit key makes the behaviour independent of that implementation detail and avoids the re-indexing cliff of a shared cache.
- **Q:** Mechanism for the interface-method false positives — definition verification, kind-gated auto-scope, defaulting `--within`, or warn-only? **A:** Definition verification — the only option with no false-negative risk in a safety gate; the others trade one error class for a worse one.
- **Q:** Where does the filter apply, and what is the escape hatch? **A:** `assert-no-callers` only, default-on, `--no-verify` to disable. The cost of N extra round trips belongs where a false positive actually blocks something; on `refs` it would be visible latency for no gain.
- **Q:** Concrete shape of the registry template — nested YAML map, two flat fields, or a JSON-fragment string? **A:** YAML-native nested map with `{{tags}}`; avoids stringly-typed JSON-in-YAML and lets future languages contribute their own shape without engine changes.
- **Q:** What happens when `--build-tags` is passed for a language with no template? **A:** Hard error before spawn. Silently ignoring a precision flag is the exact failure mode issue #2 complains about — it must either work or fail loudly.
- **Q:** What counts as a match, and what happens when verification itself fails? **A:** Exact positional match against the declaration set; an unverifiable reference stays a violation (fail-closed). A flaky server must never be able to turn the gate green by quietly weakening verification.
- **Q:** Round-trip budget for verification — bounded concurrency, sequential, or a cap on refs verified? **A:** ~~Bounded concurrency sharing one phase deadline.~~ **Superseded in review round 1** — see the `sequential-verification` decision and the r1 entry below. Bounded concurrency is unsafe against the single-flight `lsp.Client`; the answer is strictly sequential under one phase deadline. A cap on refs verified was rejected in both rounds for introducing a threshold-dependent blind spot.
- **Q:** Test coverage split? **A:** Hermetic tests for the pure parts plus `-tags lsp` live tests for both end-to-end behaviours. Build-tag visibility and interface conflation are precisely the symptoms that cannot be reproduced without a real gopls; a fake server would test wiring, not the actual problem.
- **Q:** (review r1) The concurrency premise is false — `lsp.Client` is single-flight. Sequential, or fix the transport? **A:** Sequential under one phase deadline, plus a follow-up issue for the transport limitation. The concurrency need rested on a performance assumption that does not survive the source; adding a mutex and pending-request registry to a transport every verb depends on, to save a fraction of a second on one verb, is not justified. The follow-up issue matters because an unrecorded known limitation disappears.
- **Q:** (review r1) The `tags-<hex>` state-dir segment does not partition the native strategy's shared `-remote=auto` daemon. Disposition? **A:** Spawn a private gopls on the native path when tags are non-empty. It is the only option that does not reintroduce the unverified per-session-view assumption already rejected — and since native is the only path on windows rather than merely a fallback, silent tag mixing there would be a correctness problem, not an edge case. Cold-spawn latency is acceptable because it is isolated to tagged queries; hard-erroring would make `--build-tags` unusable where native is the only path, and deferring would leave windows silently wrong.
- **Q:** (review r5) Verification would drop interface-dispatch callers when the query is a concrete method — a false negative. Disposition? **A:** Widen the declaration set with `textDocument/implementation` at the query position, symmetrically, and keep a reference matching either half. gopls unifies interface and implementer references in both directions, so definition-only matching is safe in one direction and fail-open in the other. The precision cost is small: it re-admits genuine implementers, not the unrelated structurally-identical interfaces issue #1 measures.
- **Q:** (review r5) Is tag normalization the caller's obligation or the engine's? **A:** Both — a shared `registry` function, called by the CLI for state-dir keying and re-applied defensively by the engine. `Options.BuildTags` is public, and unlike `StateDir` (whose misuse fails loudly) an unnormalized tag set fails silently, changing which daemon is used and whether the flag is honoured.
- **Q:** (review r5) Do the other `docs/` findings records get updated? **A:** No — they are dated records, accurate for when they were written, and this task answers their open question rather than falsifying it. `scout-multilang.md:17` is the lone exception because it is an arithmetic error contradicting its own counts, in this task's primary evidence document.
- **Q:** (review r4) A placeholder-free template would silently swallow `--build-tags`. Is the hard-error predicate "no template" or "no `{{tags}}`"? **A:** No `{{tags}}` anywhere in the template — absent, empty, and placeholder-free templates all fail identically. `initialization_options` is a build-tag template only, never a general static-config channel; the static-config reading existed solely to bless the case that reintroduces the silent-ignore bug, and whole-entry overlay replacement makes that case the default outcome of an operator edit.
- **Q:** (review r4) What polarity is the verification boolean on `Options`? **A:** `SkipVerification bool`, so the zero value verifies. `Options` is re-exported as the public `quarry.Options`, and a `Verify bool` would make fail-open the struct's zero value for every non-CLI caller.
- **Q:** (review r3) What is sent when the tag set is empty but the entry carries a `{{tags}}` template? **A:** No `initializationOptions` key at all — the `initialize` request stays byte-identical to today's. Sending `-tags=` or an empty list would silently change every untagged Go query's session config and contradict the back-compat promise the other two mechanisms make.
- **Q:** (review r3) The native private-spawn cost was stated per invocation, but batch mode makes one engine call per argument. Accept or fix? **A:** Accept explicitly and record it, plus a follow-up issue for batch connection reuse. An N-symbol tagged batch on native pays N cold starts; sharing one connection needs an engine-level batch entry point, a much larger change than either issue asks for, and it should serve the supervised path too rather than being bolted onto the fallback.
- **Q:** (review r2) What happens when the declaration-side definition call returns empty or errors? **A:** Skip verification entirely and keep every reference. An empty declaration set is a silent success, not an error, and nothing intersects an empty set — so verifying against it would drop every reference and exit 0, inverting today's behaviour and failing the safety gate open. Skipping preserves today's degraded-case behaviour exactly.
- **Q:** (review r2) Does a verification-phase deadline set `lookup`'s `timedOut` flag? **A:** Yes — while still returning a successful result with the unverified references kept; disposal and result semantics are independent. ~~Hard-kill on teardown.~~ **Corrected in review round 3:** setting the flag does not mean hard-kill everywhere. `teardownConnection` hard-kills only for `ConnKindNative` / `ConnKindLegacy`; for `ConnKindSupervised` — the dominant Go path — it returns with no kill and no close, by design. See `sequential-verification`'s per-`ConnKind` consequence.
- **Q:** (review r1) What does the one-connection entry point return, and which path does `--no-verify` take? **A:** A `(references, declaration, error)` tuple, with `--no-verify` calling the same entry point with verification off. A verify/no-verify pair of pipelines is duplicated logic to keep in sync by hand; having the engine return only violations would push `--except`/`--within` semantics into the engine, breaking the layering `layering_test.go` enforces; and a struct is YAGNI at two fields, convertible later if a third appears.
